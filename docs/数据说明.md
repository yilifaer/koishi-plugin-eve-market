# 数据说明

插件用到的数据从哪里来、多久更新一次、你要不要做什么、怎么看现在用的是哪个版本，以及这些数据的许可。

## 一览

| 数据 | 从哪里来 | 多久更新 |
|---|---|---|
| 物品、工业、星图（物品的中英文名和拼音、体积、蓝图、星系、空间站……） | eve-cn-slang 仓库的 `official/data/`，由 CCP 发布的静态数据（SDE）生成 | eve-cn-slang 每周三自动生成一次；插件每 6 小时在线检查一次 |
| 黑话表（简称、常用叫法） | eve-cn-slang 仓库的 `glossary.yaml`，人工维护 | 插件每 6 小时在线检查一次 |
| NPC 市场、星系、星域的价格 | EVE 的 ESI 接口（欧服） | 按 ESI 给的缓存时间，大约 5 分钟 |
| 联盟建筑市场的价格 | ESI，用服务角色的 EVE 授权读取 | 大约每 5 分钟整站同步一次 |
| 走势 | ESI 的星域成交历史 | 一天一次 |
| 入侵、服务器状态 | ESI | 5 分钟、30 秒 |
| 势力图、联盟势力图 | Verite 网站的图片 | 本机缓存 60 分钟 |
| 战报截图 | BR 工具的战报页面 | 同一个链接 10 分钟内用缓存 |
| KB 人物卡 | zKillboard（战绩统计、击杀、损失）、ESI（人物、军团、联盟、军团史、空间站）、images.evetech.net（头像、军团和联盟图标、舰船图） | 统计 60 分钟、击杀 / 损失列表 30 分钟、成品 60 分钟 |
| 数据里还没有的新物品 | ESI，按完整名字查 | 结果存 7 天（查不到也记 7 天） |

## 物品、工业、星图数据

插件认物品、算体积、找星系和空间站，都靠这份数据（目前约 2.7 万种物品）。

### 里面有什么

`industry.json` 里是工业用的表。0.0.5 起多了两张（数据版本 `dataRevision` 从 1 变成 2，数据格式 `schema` 不变，还是 1）：

| 表 | 内容 | 用在哪里 |
|---|---|---|
| `services`（建筑服务） | 每个服务装备（屹立制造厂、旗舰级船坞、超级旗舰级船坞、三种反应堆、提炼模块）能造哪些分组和大类、能装在哪些建筑上、在高安 / 低安 / 00 哪些能用 | 判断哪个地点、哪座建筑造得了这个产品；自动挑建筑只在造得了的里面挑 |
| `reprocessing`（提炼产出） | 只有 17 种「粗糙的…」产物：提炼一次的数量、提炼出什么，以及有没有专用的提炼技能 | 炼金术 |

- 两张表都是从 SDE 推出来的，规则写在 eve-cn-slang 的 `scripts/build_data.py`，插件里不写物品清单。CCP 以后加了新的服务装备，不认识的会记在变化说明里，不让每周的自动更新失败。
- 数据里 17 种「粗糙的…」如果以后出现了专用的提炼技能，「市场状态」会报「X 有专用提炼技能，炼金术不计算这一种」。

### 从哪里来

1. CCP 发布游戏的静态数据（SDE），一般在每周二的游戏更新以后。
2. eve-cn-slang 仓库里有一个自动任务（GitHub Actions 里的 **update-official**），**每周三北京时间 20:17** 运行一次：下载最新的 SDE，生成插件用的数据，也就是 `official/data/` 里的 4 个文件（`manifest.json`、`types.json`、`industry.json`、`universe.json`）。
3. 数据有变化、并且检查通过，就**直接提交到 `main`**。提交说明是「更新插件数据（build 3586130）」这样的一句。插件读的就是 `main`。
4. SDE 没有变化时，什么都不做。

想马上跑一次（例如 CCP 临时发了更新）：

1. 在 GitHub 上打开 eve-cn-slang 仓库。
2. 点上面的 **Actions**。
3. 左边点 **update-official**。
4. 右边点 **Run workflow**，再点绿色的 **Run workflow**。
5. 几分钟后刷新页面，最上面那一次前面是绿色的勾就是成功了。

### 每周要不要点合并

- **插件数据：不用。** 检查通过就自动进 `main`，插件几个小时内自己拿到。
- **官方中英名称表**（`official/eve-official.json`、`official/eve-official.csv`）：有变化时，自动任务会开一个合并请求「更新官方中英名称表」，**要你点一下合并**。这个表是给 dcqq-bridge 用的，**本插件不读它**，晚几天合并不影响查价。

点合并的步骤：

1. 在 GitHub 上打开 eve-cn-slang 仓库，点上面的 **Pull requests**。
2. 点「更新官方中英名称表」。
3. 说明里列出了哪些名字变了，扫一眼。页面上可能没有检查结果（自动开的合并请求不会触发检查，自动任务在开它之前已经检查过一遍），这是正常的。
4. 往下点 **Merge pull request**，再点 **Confirm merge**。
5. 页面提示可以删除分支（**Delete branch**），点不点都行。

### 插件怎么拿到新数据

1. 插件启动时（在控制台保存配置、插件重载时也一样），从下面三份里挑**最新**的一份马上用上：
   - 重载之前正在用的那份；
   - 本机缓存里的（以前在线下载的）；
   - 插件自带的快照。
2. 启动 20 秒后在线检查一次，以后大约每 6 小时一次（每次前后差几十分钟，错开整点）。
3. 每次只问一个很小的文件 `manifest.json`：有没有比手上更新的版本？没有就结束，几乎不占流量。
4. 有新版本：把三个数据文件一起下载下来（目前加起来约 5.6 MB），逐个核对。全部通过才写进本机缓存，然后**一下子换上**。不用重启，群友感觉不到。
5. 任何一步失败（网络不通、文件不完整、格式不对），都**继续用手上的版本**，6 小时后再试。一直失败时，日志里只写第一次。

下载地址在控制台「高级」里（`advanced.manifestUrl`）：先试 GitHub，不行再试 jsDelivr。jsDelivr 有缓存，新数据最多可能晚 12 小时左右才到。

插件会核对这些（不用记，出问题时「市场状态」里会写原因）：

- 每个文件的校验值（sha256），防止下载到一半，或者两个网站的缓存不一致；
- 数据格式的版本和插件一致；
- 每张表的行数至少是现在的 80%，防止换上一份残缺的数据；
- 黑话表的词条数至少是插件自带那份的一半。

### 本机缓存

- 位置：Koishi 实例目录下的 `data/eve-market/cache/`。
- 里面是在线下载的数据和黑话表，还有建筑市场的订单、势力图这些缓存。
- 删掉也没关系：下次启动先用插件自带的快照，20 秒后在线重新下载。
- **不要删它旁边的 `data/eve-market/secret.key`**：那是 EVE 授权用的密钥，见 [EVE授权.md](EVE授权.md) 的「换电脑、备份」。

### 插件自带的快照

- 每个版本的插件都带着一份数据快照（插件包里的 `data/` 目录），是发布那个版本时 eve-cn-slang 上的数据。
- 什么时候用它：第一次启动、还没联网时；本机缓存坏了时；控制台「高级」里的网址留空时（这时不联网，只用它）。
- 它只在升级插件时才变新。所以长期不联网的话，数据会停在那个版本发布的时候。

### 旧数据（没有新表）会怎样

数据版本是 1 的旧数据（没有 `services` 和 `reprocessing` 两张表）插件照样能用，只是：

- 不按产品筛地点和建筑（所有地点都当作造得了）；
- 不提供炼金术，「反应:炼金」按正常路线算；
- 「市场状态」的数据部分多一行「数据较旧：地点不按产品筛选、炼金术不可用」。

什么时候会碰到旧数据：用的是旧版插件自带的快照、本机缓存里还是旧的，而且在线检查还没换上新的。0.0.5 自带的快照已经是版本 2。新数据换上以后，不会被缺这两张表的数据替换掉（行数检查：新数据少了这两张表会被拒绝，继续用手上的）。

反过来，旧版插件（0.0.4 及以前）读到版本 2 的数据也没问题：它们只读自己要的表，多出来的两张表直接忽略。

### 数据格式变了

以后 eve-cn-slang 如果改了数据格式（不兼容的那种），旧版插件**不会**用新格式的数据，继续用手上的版本：

- Koishi 日志里写一句「在线的物品数据格式和插件不一致，继续用手上的版本：…请升级插件」；
- 「市场状态」的「物品数据」下面多一行「最近一次在线检查失败：…的 schema 是 N，比插件支持的 1 新，请升级插件」这样的话。

这时升级插件就好。

### 新物品

两次每周更新之间新上的物品，本地数据里还没有。这时插件会拿**完整的名字**（中文或英文全名）去问 ESI，查到了就能查价，结果存 7 天。

- 只认完整名字。简称、拼音、模糊搜索要等每周数据更新以后才能用。
- 第一次查可能慢一点：最多等 3 秒，没等到就先回答「没有找到」，查询在后台接着做完，过一会儿再查就有了。
- ESI 也查不到（例如名字写错，或者 ESI 还没收录）时，这个「查不到」同样记 7 天，这期间不会再去问 ESI。等每周数据更新收录了这个物品，就能直接查。

### 活动物品和改过名的物品查不到

有些名字在插件的数据里找不到，批量估价会写「没有找到」，后面带一句「可能是活动物品或者改过名的船」的提示。例如 `AIR Agility Booster II`、`AIR Repairer Booster III`：用 ESI 的 `/universe/ids` 按这几个英文名查，同样什么也查不到，所以这些名字很可能不是游戏里已发布物品的正式名字。「没有找到」是对的，不是写错了，也不是插件坏了。

## 黑话表

- 来源：eve-cn-slang 的 `glossary.yaml`，是人工维护的 EVE 中文黑话表。
- 插件用它给物品加别名，「翻译」的中英对照也用它。
- 和物品数据一起，每 6 小时在线检查一次，有变化就换上。
- 想加一个叫法，两个办法：
  - **只给本插件用**：控制台「物品别名」里加一行（见 [控制台配置.md](控制台配置.md)），保存就生效。
  - **让 dcqq-bridge 等别的工具也能用**：改 eve-cn-slang 的 `glossary.yaml`（格式见那个仓库的 README），进了 `main` 以后，插件 6 小时内自己拿到。
- 两边冲突时，以控制台「物品别名」为准。

## 价格和其他在线数据

### ESI

- ESI 是 CCP 给第三方程序用的官方接口。插件只查欧服（Tranquility）。
- 插件遵守 ESI 的规则：同一个请求在 ESI 给的缓存时间之内不重复请求；按 ESI 的限流放慢速度。所以「市场状态 刷新」也只会重新同步已经过期或出错的建筑市场。
- 每个请求都带着插件的名字和项目地址；控制台「高级」里填了 `esiContact` 的话也带上，出问题时 CCP 能联系到你。
- 「市场状态」里的「ESI 配额」一行是剩余的请求额度，一般不用管。看到「⚠ 错误太多（420），全部请求暂停到 …」时，到那个时间会自动恢复。
- EVE 每天例行维护（DT）：北京时间 19:00–19:30（EVE 时间 11:00–11:30）。这段时间 ESI 可能出错，有缓存时写「DT 维护中，显示维护前数据」；取不到价格时，市场格写「暂时取不到价格」，卡片上另有一句「EVE 每日维护中（北京时间 19:00 左右），价格暂时取不到，15 分钟后再试」，维护完自动恢复。

### 多久刷新、出错时怎么办

| 数据 | 刷新 | 出错时 |
|---|---|---|
| NPC 市场、星系、星域的订单 | 按 ESI 的缓存时间（约 5 分钟） | 最多显示 60 分钟以内的旧价格，并标出是多久以前的 |
| 联盟建筑市场 | 约 5 分钟整站同步一次；24 小时没人查就暂停，有人查时自动恢复 | 同步异常：最多显示 60 分钟以内的旧价格。授权异常：不显示旧价格。详见 [EVE授权.md](EVE授权.md) 的状态表 |
| 走势（成交历史） | 一天一次（ESI 每天更新） | 最多用 48 小时以内的 |
| 入侵 | 5 分钟 | 最多用 1 小时以内的 |
| 服务器状态 | 30 秒 | 最多用 5 分钟以内的 |
| 势力图、联盟势力图 | 60 分钟 | 发缓存里的旧图 |
| 战报截图 | 同一个链接 10 分钟 | — |
| Janice 估价 | 读过的估价放 6 小时（价格创建时就定了），没有这份估价记 10 分钟，连不上记 30 秒 | 回复「暂时连不上」，不显示旧数据 |
| KB 人物卡 | 缓存的是精简后的结果，不存 zKillboard 的原始响应；统计 60 分钟，击杀 / 损失列表 30 分钟，成品资料 60 分钟；ESI 的人物 1 小时，军团、联盟、军团史 1 天，空间站 7 天；头像 24 小时，其他图片 7 天；zKillboard 上查无此人记 10 分钟 | zKillboard 取不到（含被限流）：照样出卡，写「战绩暂缺」；zKillboard 上确实没有记录的人才写「查无此人战绩」；ESI 的人物信息取不到：回「欧服接口暂时连不上」 |

### Janice 估价（第三方）

Janice 是第三方网站，不是 CCP。机器人只读你们已经在 Janice 上做好的估价（按链接里的编号请求一次，用控制台里填的 API 密钥），不会把清单、QQ 号、群号发给 Janice；估价里的备注和原始粘贴文字不读取、不显示、不保存，没认出来的行只数个数。

### KB 人物卡（第三方和官方数据）

- **zKillboard**（第三方）：人物统计、该人物的击杀和损失列表（各最多 200 条）。一张卡最多请求 3 次，和「击杀」共用同一个排队通道，每次间隔至少 1 秒；zKillboard 会把统计请求 302 跳转到 `/kills/`，插件只跟随同一主机 `/api/` 下的跳转。人物简介（info.description）带链接和广告，从不读取、不显示。
- **ESI**（官方）：人物公开信息（名字、建号时间、军团头衔）、军团、联盟、军团史（最早的一条是新手军团）、新手军团的母港空间站。照片说明「摄于 …」就是这个空间站的名字，任何一步取不到写「摄于新伊甸某处」。
- **images.evetech.net**（官方图片）：头像、军团和联盟图标、舰船图。由插件下载后嵌进页面，出图用的浏览器本身不联网；只接受 PNG / JPEG，大小和时间都有上限，下载失败的图空着，不影响出卡。
- **名字模糊搜索**：用「市场授权」那个角色的令牌调用 ESI 的搜索，只读；没做过市场授权就不能模糊搜索。
- 什么都不存到磁盘：缓存全在内存里，重启就没有。**不记录谁查了谁**：日志里没有查询人，也没有人物名；人物 ID 只出现在少数几行里：资料组装失败和出图失败（警告），以及 zKillboard 统计取不到、出生地查不到、军团或联盟信息取不到（调试）。
- 近期大击杀 / 大损失只看最近 30 天；活跃时段按击杀和损失的时间（UTC）分小时，北京时间在前、EVE 时间在括号里；不到 10 条记录时改用 zKillboard 的时区标签，只写「主要活跃时段：…」。

## 怎么看现在用的数据版本

管理员私聊机器人（或者在授权群里 @机器人）发：

```
市场状态
```

卡片中间有这样两行（数字只是举例）：

```
物品数据：SDE build 3586130 · 来自在线（14:01 确认最新）
黑话表：在线 · 371 条 · 别名接入 1,024 个
```

- `SDE build 3586130`：这份数据是从哪个版本的 CCP 静态数据生成的。数字越大越新。
- 「来自在线」：这次运行时在线下载的。
- 「来自本机缓存」：以前下载、存在本机的。例如刚重启，还没到在线检查的时候。
- 「插件自带」：插件包里的快照。
- 「（14:01 确认最新）」：插件最近一次在线确认「没有更新的版本」的时间。
- 黑话表那一行：从哪里来、有多少条、接进来多少个别名。

和 eve-cn-slang 上的最新版本对一下：在 GitHub 上打开 eve-cn-slang → `official/data/manifest.json`，里面的 `buildNumber` 就是最新的 build。和「市场状态」里的一样，插件用的就是最新的。

### 马上检查一次

发 `市场状态 刷新`（或者点卡片上的「立即刷新」）。卡片标题下面多一行「刷新结果」：

| 刷新结果里写 | 意思 |
|---|---|
| 物品数据在线确认是最新 | 没有新版本 |
| 物品数据已更新到 SDE build … | 刚刚换上了新数据 |
| 物品数据在线检查失败（…） | 连不上，或者下载的文件不对，括号里是原因。继续用手上的版本 |
| 物品数据没有设置在线网址，只用插件自带的 | 控制台「高级」里的网址是空的 |
| 黑话表已更新 | 刚刚换上了新的黑话表 |
| …没做完的在后台接着做，稍后再发「市场状态」看结果 | 10 秒内没做完，过一会儿再看 |

### 提醒和警告

| 「市场状态」里看到 | 意思 | 怎么办 |
|---|---|---|
| 物品数据：加载中 | 插件刚启动 | 等几秒再发 |
| ⚠ 物品数据已经 N 天没更新（…） | 插件已经超过 14 天没能在线确认数据是最新的。从来没在线确认过时（例如网址留空、只用自带数据），按数据生成的时间算 | 看下一行「最近一次在线检查失败」写的原因；确认 Koishi 那台电脑能打开 raw.githubusercontent.com 或 cdn.jsdelivr.net。只用自带数据时，升级插件就会换上新的快照 |
| 最近一次在线检查失败：… | 上一次在线检查没成功 | 偶尔一次不用管，6 小时后自动再试；一直这样就看原因，或者把这一行告诉开发者 |
| 数据较旧：地点不按产品筛选、炼金术不可用 | 手上的数据没有「建筑服务」「提炼产出」两张表（数据版本是 1） | 不影响查价；等下一次在线检查换上版本 2 的数据，或者升级插件换上新的快照 |

### eve-cn-slang 的每周任务有没有在跑

插件这边一切正常，不代表 eve-cn-slang 那边每周都在生成新数据。偶尔去看一眼：

1. 在 GitHub 上打开 eve-cn-slang → **Actions** → 左边 **update-official**。
2. 最近几次运行，前面应该是绿色的勾，大约每周三一次。
3. 是红色的叉：点进去，可以点 **Re-run jobs** 重跑一次；还是失败，就把页面上的错误告诉开发者。
4. 页面上方提示定时任务被停用了：GitHub 对很久没有新提交的公开仓库会自动停掉定时任务（具体多久待核实）。点 **Enable workflow** 重新打开。
